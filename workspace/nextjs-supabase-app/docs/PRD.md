# 모임 이벤트 관리 MVP PRD

## 🎯 핵심 정보

**목적**: 모임 주최자가 공지, 참여자 관리, 카풀, 정산을 흩어진 카톡/엑셀 없이 한 곳에서 처리하게 한다.
**사용자**: 수영/헬스 같은 정기 모임과 친구 모임 같은 비정기 모임을 운영하는 주최자 및 그 참여자.

## 📌 배경

기존 `nextjs-supabase-app` 저장소(Next.js 15 App Router + Supabase Auth 스타터킷)에 이어서 개발하는 신규 기능이다. 별도 프로젝트가 아니며, 기존 인증 플로우(`app/auth/*`, `app/protected/*`, proxy 세션 체크)를 그대로 활용한다.

> **참고**: 이벤트 관련 라우트는 `app/events/*`에 위치한다(`app/protected/*` 그룹 밖). 다만 `lib/supabase/proxy.ts`의 인증 체크는 `/`, `/auth/*`, `/login`을 제외한 전체 경로에 전역 적용되므로 `/events/*` 역시 보호된 라우트다.
>
> Task 001~003(도메인 타입/패키지 설치, 라우트 골격, 더미 데이터 기반 UI)은 이미 완료되었으며, 본 PRD는 그 위에 신규 기능(이벤트 유형, 강퇴, 초대, 블랙리스트, 친구, 관리자 페이지)을 추가 정의한다.

## 🚶 사용자 시나리오

### 시나리오 1: 정기 모임 (수영 강습)

1. 주최자가 로그인 후 이벤트 생성 페이지에서 "화요일 저녁 수영 강습" 이벤트를 만든다.
2. 같은 일정을 여러 번 반복해야 하면, 주최자가 매주 동일한 내용으로 이벤트를 다시 생성한다(반복 규칙 자동화 없음).
3. 고정 멤버들이 각 회차 이벤트에 참여 신청을 한다.
4. 정원 초과 시 신청자는 대기자로 등록되고, 기존 참여자가 취소하면 대기자가 자동으로 승격된다.
5. 모임 종료 후 주최자가 정산 항목(강습비 등)을 만들면 참여자 수만큼 1/N 금액이 계산된다.
6. 참여자가 실제로 입금하면 주최자가 해당 참여자의 정산 상태를 "완료"로 표시한다.

### 시나리오 2: 비정기 모임 (친구 모임 + 카풀)

1. 주최자가 "이번 주말 캠핑" 이벤트를 1회성으로 생성하고 공지사항(집합 장소, 준비물)을 작성한다.
2. 참여자들이 참여 신청을 한다.
3. 차량이 있는 참여자가 카풀 운전자로 등록(좌석 수, 출발지, 출발 시간)한다.
4. 다른 참여자가 카풀 탑승을 신청하면 운전자 또는 주최자가 매칭을 확정한다.
5. 모임 후 주최자가 정산(캠핑장 비용, 식비 등 항목별)을 등록하면 참여자별 분담액이 계산되고, 입금 여부를 개별 체크한다.

## ⚡ 기능 요구사항

### F001. 이벤트 생성/관리

- **설명**: 주최자가 이벤트(모임)를 생성, 수정, 삭제하고 공지사항을 작성한다.
- **필드**: 제목, 설명/공지사항, 일시, 장소, 정원(최대 인원), 상태(모집중/마감/종료), **참여 방식(`join_type`: 선착순/비밀번호/승인)**, **비밀번호(`join_type`이 비밀번호일 때만 입력, 서버에 해시 저장)**, **이벤트 일정(`schedule`, 선택)**, **준비물(`items_to_bring`, 선택)**, **반복 설정(`recurrence_type`: 없음/매일/매주/매달 N번째 요일/매달 특정 일자 + 관련 요일·주차·일자·시간 하위 필드)**
- **공지 탭 표시 항목**: 설명, 이벤트 장소, 이벤트 일시, **현재 확정 참석자 수(`확정 인원 / 정원`)**, 이벤트 일정(입력된 경우), 준비물(입력된 경우). 참여를 고민하는 사용자가 현재 참여 인원을 보고 신청 여부를 판단할 수 있도록 공지 탭에서 항상 노출한다.
- **정기 모임 처리**: 반복 설정(`recurrence_type`)은 생성 폼에서 매일/매주 특정 요일/매달 N번째 요일/매달 특정 일자 패턴을 선택할 수 있게 하되, 실제 반복 occurrence 자동 생성 로직은 MVP 범위 밖이며 반복 정보는 안내 표시 용도로만 저장한다.
- **권한**: 이벤트는 주최자(생성자)만 수정/삭제 가능. 모든 로그인 사용자는 이벤트 목록 조회 및 생성 가능(단, F009 블랙리스트에 등록된 주최자의 이벤트는 조회에서 제외).
- **참여자/카풀/정산 탭 접근 제한**: 참여자 탭, 카풀 탭은 주최자 또는 확정(`confirmed`) 참여자만 열람 가능하다. 그 외 사용자에게는 잠금 안내(`참여가 확정된 참여자만 볼 수 있는 정보입니다.`)를 표시한다. 정산 탭은 F004의 공개 설정을 추가로 따른다.
- **관련 페이지**: 이벤트 목록 페이지, 이벤트 생성 페이지, 이벤트 상세 페이지

### F002. 참여자 관리

- **설명**: 참여 신청/취소, 참석자 목록 확인, 정원 초과 시 대기자 처리, 주최자의 참여자 강퇴.
- **동작 규칙**:
  - 참여 신청 시 이벤트의 `join_type`에 따라 분기한다.
    - 선착순: 현재 확정 인원이 정원 미만이면 즉시 "확정", 정원이 찬 경우 "대기" 등록.
    - 비밀번호: 입력한 비밀번호가 이벤트 비밀번호와 일치하면 위 선착순 규칙과 동일하게 확정/대기 처리, 불일치 시 신청 거부.
    - 승인: 신청 시 "승인 대기(`pending_approval`)" 상태로 등록되며, 주최자가 승인해야 "확정"으로 전환.
  - 확정 참여자가 취소하면, 대기자 중 신청 순서가 가장 빠른 사람이 자동으로 "확정"으로 승격.
  - 주최자는 참여자 목록에서 상태(확정/대기/승인대기/취소/강퇴)를 확인하고 강제 취소 또는 **강퇴** 처리 가능.
  - **강퇴**: 주최자가 참여자를 강퇴할 때 사유를 작성한다. "사유 비공개" 체크박스를 선택하면 해당 사유는 당사자에게 전달되지 않는다. 강퇴된 참여자는 자진 취소(`cancelled`)와 구분되는 별도 상태 `kicked`로 전환되며, `kicked_at`/`kick_reason`/`kick_reason_visible`이 함께 기록된다.
- **관련 페이지**: 이벤트 상세 페이지(참여자 탭)

### F003. 카풀 관리

- **설명**: 운전자가 좌석 수와 출발지/시간을 등록하고, 탑승자가 신청하거나 운전자가 직접 초대하는 양방향 매칭을 지원한다.
- **탑승자 상태(`carpool_passengers.status`)**: 초대중(`invited`) / 신청(`requested`) / 확정(`confirmed`) / 거절(`rejected`) 4가지. 어느 쪽이 먼저 제안했는지 구분하기 위해 `initiated_by`(운전자/탑승자) 값을 함께 기록한다.
- **동작 규칙**:
  - 참여자(확정 상태)는 "운전자로 지원하기"를 통해 카풀 운전자로 등록 가능(좌석 수, 출발지, 출발 시간 입력).
  - **운전자 → 탑승자 초대**: 운전자는 확정 참여자 중 아직 활성 상태(초대중/신청/확정)가 아닌 사람을 선택해 초대할 수 있다. 초대받은 사람에게는 `초대중` 상태로 표시되며, 본인은 수락/거절 버튼으로 응답한다.
  - **탑승자 → 운전자 신청**: 확정 참여자는 자신이 운전자가 아닌 카풀에 "카풀 신청하기"로 직접 탑승을 신청할 수 있다. 신청 건은 `신청` 상태로 표시되며, 해당 카풀의 운전자에게 수락/거절 버튼이 노출된다.
  - **운전자의 거절**: 운전자가 신청 건을 거절하면 상태가 `거절`로 바뀌고, 거절당한 탑승자는 **동일 운전자에게 다시 신청할 수 없다**(재신청 버튼 비노출, 안내 문구 표시).
  - **재초대 허용**: 운전자가 실수로 거절했거나 탑승자가 초대를 거절한 경우를 대비해, 카풀 초대 대상자 목록에는 현재 활성 상태(초대중/신청/확정)가 아닌 모든 확정 참여자가 다시 표시된다(거절 이력이 있어도 노출 제외하지 않음). 단, 운전자가 신청을 거절해 재신청이 막힌 사람도 운전자가 먼저 재초대하는 것은 가능하다.
  - 탑승 신청/초대는 잔여 좌석 수와 무관하게 접수되며(좌석 초과 시 별도 대기열 없음, MVP 범위 밖), 확정 여부는 운전자/탑승자의 수락 여부로만 결정한다.
  - **운전자 간 초대 제한**: 운전자는 초대 대상자 목록에서 이벤트 내 다른 카풀의 운전자(자기 자신 포함)를 초대할 수 없다. 이미 다른 운전자로 등록된 참여자는 목록에서 제외한다.
  - **확정된 탑승자 초대 제한**: 운전자는 이미 다른 운전자의 카풀에 `확정(confirmed)`된 탑승자를 초대할 수 없다(한 사람이 동시에 두 카풀에 확정 탑승할 수 없음). `초대중`/`신청` 등 미확정 상태로만 걸려 있는 사람은 여전히 초대 대상 목록에 노출된다.
  - **탑승자의 운전자 지원 시 경고**: 이미 다른 운전자에게 `초대중`이거나 `신청` 상태로 걸려 있는 참여자가 "운전자로 지원하기" 버튼을 클릭하면, 곧바로 지원 폼을 열지 않고 현재 상태에 맞는 확인 알림을 먼저 보여준다.
    - `초대중`인 경우: "OO님의 카풀에 탑승 초대를 받은 상태입니다. 그래도 운전자로 지원하시겠습니까?"
    - `신청` 중인 경우: "OO님에게 카풀 탑승을 신청한 상태입니다. 그래도 운전자로 지원하시겠습니까?"
    - `확정`인 경우: "이미 OO님의 카풀에 탑승이 확정된 상태입니다. 그래도 운전자로 지원하시겠습니까?"
    - 알림에서 "무시하고 지원하기"를 선택하면 운전자 등록을 진행하는 동시에, 기존에 걸려 있던 다른 운전자 카풀의 탑승자 레코드(초대중/신청/확정 불문)를 자동으로 제거해 그 운전자의 탑승자 목록에서 사라지도록 한다. 취소를 선택하면 운전자 지원을 중단하고 기존 탑승 상태를 유지한다.
- **관련 페이지**: 이벤트 상세 페이지(카풀 탭)

### F004. 정산

- **설명**: 이벤트 비용을 참여자 수로 나눈 1/N 금액을 계산하고, 참여자별 완료 여부만 기록한다.
- **정산 내역 공개 범위(`settlement_visible`)**: 이벤트 생성 시 주최자가 정산 내역을 참여자 전체에게 공개할지, 주최자 본인만 열람할지 선택한다. 친구들끼리의 모임처럼 투명성이 중요한 경우 공개(기본값), 특강처럼 금액을 공유하고 싶지 않은 경우 비공개로 설정한다.
- **동작 규칙**:
  - 주최자가 정산 항목(예: "강습비", "캠핑장 비용")을 생성하고 총액을 입력.
  - 시스템이 정산 대상 참여자(확정 상태) 수로 총액을 나눠 1인당 분담액을 자동 계산.
  - 각 참여자별로 "입금 완료 / 미완료" 상태만 주최자가 체크.
  - 실제 결제/송금 연동은 하지 않는다(계좌번호 안내 등 수동 처리 전제).
  - 주최자는 항상 정산 탭을 열람할 수 있다. 참여자는 `settlement_visible`이 공개일 때만 열람 가능하며, 비공개일 경우 "주최자가 정산 내역을 비공개로 설정했습니다." 안내가 표시된다.
- **관련 페이지**: 이벤트 생성 페이지(공개 범위 설정), 이벤트 상세 페이지(정산 탭)

### F005. 기본 인증 (기존 기능 재사용)

- 기존 스타터킷의 회원가입/로그인/로그아웃 그대로 사용. 신규 개발 범위 아님.
- **관련 페이지**: 로그인 페이지, 회원가입 페이지 (기존 `app/auth/*`)

### F006. 나의 주최 이벤트 목록

- **설명**: 로그인 사용자가 본인이 주최한 이벤트만 모아 확인한다.
- **필드/뷰**: 전체/모집중/마감/종료 4개 카테고리 탭.
- **동작 규칙**: 주최한 이벤트가 하나도 없으면 "생성한 이벤트가 없습니다." 안내 문구를 표시한다.
- **권한**: 본인이 주최자인 이벤트만 조회.
- **관련 페이지**: 나의 주최 이벤트 페이지(`/events/mine`)

### F007. 참여 이벤트 목록

- **설명**: 로그인 사용자가 신청했거나 참가 중/참가했던 이벤트를 모아 확인한다.
- **필드/뷰**: 전체/모집중/마감/종료 4개 카테고리 탭.
- **권한**: 본인이 참여자(확정/대기/승인대기 포함)로 등록된 이벤트만 조회.
- **관련 페이지**: 참여 이벤트 페이지(`/events/joined`)

### F008. 이메일 초대

- **설명**: 주최자가 앱 가입자의 이메일 정보를 이용해 특정 유저를 자신의 이벤트에 초대한다.
- **동작 규칙**:
  - 주최자가 이벤트 상세에서 초대할 유저의 이메일을 입력하면 초대(`invitations`)가 생성된다.
  - 초대받은 참여자는 "초대 목록" 페이지에서 초대된 이벤트 정보를 확인하고 수락/거절할 수 있다.
- **권한**: 초대 생성은 해당 이벤트의 주최자만 가능. 초대 조회/수락/거절은 초대받은 본인만 가능.
- **관련 페이지**: 이벤트 상세 페이지(초대 발송), 초대 목록 페이지(`/events/invitations`)

### F009. 블랙리스트

- **설명**: 참여자가 특정 주최자를 차단해 이후 해당 주최자의 이벤트가 노출되지 않도록 한다.
- **동작 규칙**:
  - 초대 목록에서 이벤트/주최자 정보를 확인 후 마음에 들지 않으면 해당 주최자를 블랙리스트에 등록할 수 있다.
  - 블랙리스트에 등록된 주최자가 만든 이벤트는 이벤트 목록·초대 목록에서 더 이상 노출되지 않는다.
  - 목적: 주최자 프로필 또는 지속적인 스팸 초대성 이벤트를 회피하기 위함.
- **권한**: 블랙리스트 등록/해제는 본인(차단하는 참여자)만 가능.
- **관련 페이지**: 초대 목록 페이지(`/events/invitations`)

### F010. 친구

- **설명**: 앱 가입자(또는 구글 로그인 사용자) 간 친구 추가 및 친구 목록 조회.
- **동작 규칙**: 이메일/닉네임 등으로 상대를 검색해 친구 요청을 보내고, 상대가 수락하면 친구 관계가 성립한다.
- **관련 페이지**: 친구 목록/검색 페이지(`/friends`)

### F011. 관리자 페이지

- **설명**: 관리자 권한(`admin_users` 테이블에 등록된 사용자)을 가진 사용자만 접근 가능한 운영 관리 화면. 인증 자체는 기존 로그인 플로우를 재사용하되, 추가로 관리자 권한 여부를 확인한다.
- **F011-1 대시보드**: 총 이벤트 수, 총 사용자 수, 진행 중 이벤트 수, 이번 달 신규(이벤트/사용자) 수, 최근 이벤트 목록, 최근 가입 사용자 목록을 카드/목록 형태로 표시.
- **F011-2 이벤트 관리**: 이벤트 검색 필터, 목록 테이블(제목/이벤트 비밀번호/날짜/상태/호스트/참여자 수/액션). 액션은 강제 삭제, 관리자 공지 등록을 지원.
- **F011-3 사용자 관리 및 통계 분석 (최소 범위)**: 사용자 관리는 사용자 목록 조회 및 검색까지만 지원. 통계 분석은 월별 이벤트 생성 수/신규 가입자 수 추이 조회까지만 지원(엑셀 내보내기 등 없음). 사용자가 상세 요구사항을 별도로 지정하지 않아 조회 전용 최소 기능으로 범위를 한정한다.
- **권한**: `admin_users` 테이블에 등록된 사용자만 `/admin/*` 접근 가능, 미등록 사용자는 404 처리.
- **관련 페이지**: `/admin`, `/admin/dashboard`, `/admin/events`, `/admin/users`, `/admin/analytics`

## 🚫 MVP 범위 제외 (Non-goals)

- **실제 결제/송금 연동**: PG사 연동, 계좌이체 자동 확인 없음. 정산은 금액 계산과 완료 체크리스트로 한정.
- **occurrence 기반 정기 일정 관리**: 반복 규칙(RRULE 등)을 통한 자동 회차 생성 없음. 정기 모임은 매번 개별 이벤트로 수동 생성.
- **카풀 대기열/자동 매칭 알고리즘**: 좌석 초과 시 대기자 개념 없음(참여자 대기자 처리와는 별개).
- **알림/리마인더**: 이메일·푸시·문자 알림 없음(초대/친구 요청 알림 포함).
- **프로필 상세 관리**: 아바타, 자기소개 등 확장 프로필 없음(`auth.users` 기본 정보만 사용).
- **모바일 앱**: 반응형 웹으로만 제공.
- **승인 대기 자동 만료**: `pending_approval` 상태는 주최자가 수동으로 승인/거절할 때까지 유지되며 자동 만료 없음.
- **관리자 권한 등급**: super admin 등 세분화된 관리자 등급 없이 단일 admin 역할만 존재.
- **관리자 통계 내보내기**: 통계 분석은 화면 조회 전용, 엑셀/CSV 내보내기 없음.

### admin_users (관리자 권한)

| 필드 | 설명 | 타입/관계 |
|------|------|----------|
| user_id | 관리자로 지정된 사용자 (PK) | → auth.users.id |
| granted_at | 권한 부여 시각 | timestamptz |

> 관리자 권한은 Supabase custom claims(JWT app_metadata) 대신 별도 `admin_users` 테이블로 관리한다. RLS에서 `EXISTS(SELECT 1 FROM admin_users WHERE user_id = auth.uid())` 형태의 `is_admin()` 헬퍼 함수로 체크한다. custom claims 대비 매 요청 DB 조회가 1회 추가되지만, 관리자 추가/제거가 일반 CRUD로 가능해 재로그인/토큰 갱신 없이 즉시 반영되고 향후 관리 UI 확장이 쉽다는 장점이 크다.

> 10개 테이블 모두 RLS 적용, `auth.users`를 직접 FK로 참조(별도 `profiles` 테이블 없음).

## 🛠️ 기술 스펙 요약

- **베이스**: 기존 저장소(Next.js 15 App Router + Supabase Auth 스타터킷) 위에 이어서 개발
- **라우트 구조**: `app/events/` (목록) → `app/events/new` (생성) → `app/events/[eventId]` (상세, 참여자/카풀/정산 하위 탭) → `app/events/mine`, `app/events/joined`, `app/events/invitations` → `app/friends` → `app/admin/*`(대시보드/이벤트/사용자/통계)
- **데이터 조회**: 서버 컴포넌트 + `lib/supabase/server.ts`
- **폼 제출**: Server Actions (React Hook Form + Zod로 클라이언트 검증 후 서버 액션에서 재검증)
- **DB**: `events`, `participants`, `carpools`, `carpool_passengers`, `settlements`, `settlement_shares`, `invitations`, `blacklists`, `friendships`, `admin_users` 10개 테이블, 전 테이블 RLS
- **정기 모임 처리**: occurrence 테이블 없이 반복 생성되는 개별 `events` row로 단순 처리
- **관리자 권한**: `admin_users` 테이블 + `is_admin()` RLS 헬퍼 함수
- **신규 shadcn 컴포넌트**: form, dialog, select, table, tabs, textarea, avatar, calendar, popover, alert-dialog
- **신규 npm 패키지**: react-hook-form, zod, @hookform/resolvers, date-fns
- **상태관리**: zustand 도입하지 않음(서버 컴포넌트 + Server Actions로 충분)
